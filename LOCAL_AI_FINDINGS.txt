LOCAL AI ON AN INTEL CORE ULTRA MINI PC: FINDINGS LOG
=====================================================
Started 2026-09-18 (sessions of 2026-09-17/18), appended as things changed. Public edition: hostnames, addresses,
config entry ids and household details are removed; every measurement is as logged. Companion files:
casa_prompt.txt (the local "Casa" prompt), ai-eval/ (the test scripts), STT_TTS_BENCHMARKS.md (speech engines).


1. HARDWARE AND WHERE IT RUNS
-----------------------------
Box: Intel Core Ultra 7 mini PC (Meteor Lake, 6P+8E+2LP cores), 32 GB DDR5, 1 TB NVMe, Intel Arc iGPU (8 Xe cores,
shares system RAM), Intel NPU. Proxmox VE host.
AI guest ("voice host"): an LXC container on Ubuntu 26.04 (needed for Mesa 26 = working Vulkan on this iGPU),
12 cores, 20 GB memory cap (a cap, not a reservation), 100 GB disk, /dev/dri/renderD128 passed through.
Home Assistant runs in its own VM on the same host (4 vCPU).

Practical ceiling of this iGPU (measured, not theoretical):
  - text generation ≈ 6.5–10 tokens/s for 3–4B models, ≈ 5 tok/s for the 26B MoE, ≈ 14 tok/s for a 1.5B-active MoE
  - prompt reading ≈ 50–370 tokens/s depending on the model architecture
  - effective memory bandwidth ≈ 22 GB/s, so tokens/s ≈ 22 / (model size in GB). A dense 27B (16 GB) would crawl at ~1.5 tok/s.
  - every generated token costs ~150 ms, so answer LENGTH is the main latency lever, not the model.

       bigger-model quality at small-model speed (gemma4 26B-A4B ≈ 5 tok/s like a 4B, at 15.6 GB).


3. HOW THINGS WERE TESTED (scripts in ai-eval/, all need config.env exported: set -a; . ./config.env)
--------------------------------------------------------------------------------------------------
llm_bench.py MODEL [n]       Raw speed. Sends a ~2.7k-token HA-like prompt (room/light list repeated) + the trick
                             question "which rooms have a pendant?" twice: run 1 = cold prompt processing speed,
                             run 2 = warm (cache hit) + generation speed. Correct answer: kitchen and bedroom only.
tool_probe.py MODEL…         Tool-calling sanity. 6 requests with HA-style tool schemas (HassTurnOn/Off, HassLightSet,
                             GetLiveContext) and a 1k-token device list: direct command, brightness, fuzzy request,
                             area-wide off, state question, general knowledge (must NOT call a tool).
ha_agent_eval.py AGENT       The real thing. 10 commands through HA's conversation API (POST /api/conversation/process,
                             agent_id = conversation.xxx) against the real house (84 exposed entities). Checks the
                             actual entity state after each action, times every command, restores the test lights.
ha_pipeline_trace.py "text"  Why is it slow? Runs the Casa AI pipeline over WebSocket (assist_pipeline/run) and prints
                             the model's raw output per turn: text, tool calls, tool results, hidden thinking.
make_chat_model.py           Builds the "chat" preset (see 6).
Ollama journal:              journalctl -u ollama | grep -E "prompt eval time|eval time|evict|loaded runners"
                             shows per-request prompt tokens re-processed vs cached, generation tokens, evictions.
Grading rule: a command counts only if the device really changed; a question counts only if the answer is right
(read the answers: an "OK" from the script for a confident wrong answer is still a fail).

7. GOTCHAS LEARNED (the expensive ones)
---------------------------------------
- Thinking: qwen3.5 thinks unless the request carries think:false (a one-line answer took 115 s with 3,000 chars
  of reasoning). The phone app does not send think:false, so on the phone use only "chat". LFM2.5 ignores think:false
  entirely (reasoning-only model); an assistant prefill of "<think>\n\n</think>\n" skips it.
- Images: qwen3.5 turns a full-resolution photo into ~4,500 tokens (60 s to "look"); gemma3 uses a fixed 256.
- Ollama keeps one runner per (weights blob, num_ctx): "chat" and gemma3:4b share a runner; the same model at a
  different num_ctx spawns a second copy and evicts others.
- Eviction is LRU with a pessimistic memory estimate; 2 small models (≈9 GB) coexist under the 20 GB cap, the 26B
  evicts both, and HA reloads its own model on the next request (~36–70 s once). No OOM kills seen with Ollama.
- HA 2026.7.1 prompt is static (no timestamp: GetDateTime is a tool), so caching works; GetLiveContext returns
  ~1,000 tokens of state each time it is called (that is why "check state then act" doubles the time).
- rest_command in a package needed a full HA restart to appear (homeassistant.reload_all does not add domains).
- Vulkan on this iGPU corrupts Gemma 4 (12B and E4B) output on long prompts; the 26B-A4B QAT answered correctly at 2.7k.
- pkill -f <pattern> matches your own shell command line; use pkill -x.

10. HARDWARE LIMITERS: INVESTIGATED 2026-09-18 (why the iGPU only gets ~22 GB/s of the RAM's 67)
-----------------------------------------------------------------------------------------------
Checked and healthy: 2 x 16 GB DDR5-5600, one per memory controller (dual channel, full speed);
CPU memcpy bandwidth 67 GB/s (75 % of 89.6 theoretical); i915 driver, GPU requests 2250 MHz; governor
performance; 65 C under load; latest BIOS from the vendor.
Limiter 1: PL4 (peak power) throttling. While generating, the GPU actually runs 900-1500 MHz with
  /sys/class/drm/card0/gt/gt0/throttle_reason_pl4 = 1 (pl1/pl2/thermal = 0) at only ~19.6 W package.
  PL4 is set by the vendor firmware and not exposed to Linux (RAPL/MSR): BIOS only.
  PL2 was 43 W (vendor default), raised to Intel's 64 W spec via /sys/class/powercap (PL1 stays 28 W) with a host
  service at boot. Measured +12 % (10.1 → 11.3 tok/s).
Limiter 2: Vulkan Q4 kernels. Q8_0 (2x bytes) runs only 30 % slower than Q4_K_M (7.0 vs 10.1 tok/s),
  so the GPU can stream >= 27 GB/s; the 4-bit path is partly compute/kernel-bound.
SYCL backend (Intel oneAPI 2026.1, llama.cpp, fa off; fa=1 is slower: no XMX on Meteor Lake):
  llama-bench granite 3B: pp 257 / tg 18.7 (vs Vulkan 209 / 10.1), BUT at a realistic 3.5k-token context in
  server mode: tg 9.7-10.1 vs Vulkan 8.2-8.6 (+15-20 %), pp 164 vs 196 (slower). Qwen3.5 GGUF would not load
  on SYCL. Not worth a second serving stack; removed. Re-test if SYCL/Mesa improve.
Mesa: 26.0.8 in the container; no newer build available for Ubuntu 26.04 yet.
Realistic ceiling of all software/firmware fixes on this box: ~1.5-2x today. A different memory bus
  (Strix Halo, an Apple M-series Pro, a discrete GPU) is what changes the league.

13. TYPOS, QUESTIONS AND CACHE SLOTS: 2026-09-19 evening
--------------------------------------------------------
- The Canonicalizer turned a typo'd QUESTION into an ACTION ("is the montor light on?" → "Turned on the light"):
  its closest candidate was a command. Fixes: (a) the chat pipe corrects one-off typos in device/room/command words
  BEFORE the exact matcher (difflib against a vocabulary built from HA friendly names + aliases + command words,
  cutoff 0.8, refreshed every 10 min) so the exact matcher decides question vs command; (b) Canonicalizer
  min_confidence 0.5 → 0.62 so garbled input falls to the model instead of guessing an action; (c) area aliases
  ("bedroom", "bathroom", "closet", "entry"...); (d) templates for "of" typos, "would you mind turning", "tell me if
  X is on", "what's the status of X", "how warm is it in <area>"; (e) "hey/hi/ok casa ..." and trailing
  "please/thanks" stripped before matching.
  Result: typo'd commands and questions 0.0-0.3 s, questions stay questions. Still model-bound: "what's the
  temperature in the <room without thermostat>" (HA's built-in climate sentence wins over the custom one).
- Slow first replies: memory recall embeds via nomic-embed-text; with OLLAMA_MAX_LOADED_MODELS=2 that evicted a
  model every turn → now 3 resident (granite + chat + nomic, keep-warm loads all three).
- 46-67 s house answers: granite's runner had 2 cache slots for 3 prompts (house 5k tokens, chat brain, keep-warm);
  overlaps evicted the house prompt (40 s rebuild). OLLAMA_NUM_PARALLEL=3 (slot chosen by prefix similarity).
- Leaked "</think>" + duplicated text from granite in the chat: the pipe strips think blocks (also mid-stream).
- General questions in the chat: granite refuses people's physical attributes ("what is Obama's height" →
  "I don't have that information", curly apostrophe!) and the tool-heavy rules made it conservative. Now: rules
  say it is a knowledgeable general assistant, temperature 0.2, and a refusal detector re-asks the question plainly
  on the gemma "chat" model. Obama 6'1" OK, Messi 1.75 m OK, but "Taylor Swift born 1999" (wrong: 1989): 3B facts
  are unreliable; the real fix = local web search (SearXNG) or the 26B for "smart mode".

15. SPEED TUNING PASS: 2026-09-20
--------------------------------
Measured floor on this hardware: granite 10.5 tok/s generation, ~215-270 tok/s prompt reading; a 300-character answer
costs ~7 s of generation no matter what: the pipe's job is to avoid the model or shorten what it writes.
Helped:
- Open WebUI background tasks (title/tags/follow-ups/query generation) ran THROUGH the Casa pipe after every reply
  (TASK_MODEL was empty = current model): now TASK_MODEL=chat:latest, only title generation on (3 hidden model runs
  per chat removed).
- The chat container was CPU-starved (load 3.9 on 2 cores while Open WebUI + SearXNG worked): 4 cores now (load ~2).
- SearXNG waited up to 3 s for engines that never answer: disabled; request_timeout 2 s. Search 3.0 s → 0.3-0.9 s.
- Per-lane output caps: search answers 140 tokens, translations 120, brain turns 320, options quick-version 170;
  search snippets 200 chars.
- Server-status tool output compacted (600 → ~60 tokens): 13 s → 6.7 s warm.
No effect (tested, left off): OLLAMA_FLASH_ATTENTION (10.5-12.2 tok/s either way), num_batch 512/1024/2048 (215 tok/s
each). Not applicable here: speculative decoding (no Ollama support), KV quantization (memory only).
Operational rule: after ANY Ollama restart re-warm the Casa prompt (stt/ollama-keepwarm.sh), or the next voice
command pays ~40 s of cold prompt reading; and the GPU is shared, so a chat answer running at the same time drops to
~1.7 tok/s (the 51 s outlier seen that day).
Warm numbers after tuning: capital of Peru 1.8 s · a footballer's age 0.4 s · weather 0.0 s · dessert idea 5.5 s ·
a long driving-distance answer 7.8 s · server status 6.7 s.
- "Quick Google" lane: FACT questions are rewritten to keyword queries ("how far is A from B by car" → "A to B
  distance miles", "what is X's birthday" → "X born date"), results pass a relevance check (some engines fixate on
  the first word), and numeric answers are EXTRACTED IN CODE (distance, drive time, height in ft/in or metres,
  birthday with age, population). Model answers capped at 90 tokens / 20 words. Timings: distances 0.7-1.0 s, a
  landmark 0.7 s, a birthday 0.8 s, news 1.2 s, a CEO 3.0 s.
- Search answers ~1-2.5 s warm: search + Wikipedia summary fetched IN PARALLEL (asyncio.gather), the model gets a
  tiny context (wiki summary + 3 snippets x 150 chars, ~120 tokens) and replies with the bare answer phrase (max 10
  words, 40 tokens). Target: nothing over ~2.5 s for quick facts, 4 s worst.
- Two hidden causes of 40-70 s house answers, both fixed:
  (a) the keep-warm pinged conversation.casa DIRECTLY, but real requests reach Casa through the Canonicalizer and
      that path renders a different prompt (only 3 common tokens), so the ping warmed a shape nobody used. Now the
      ping goes to conversation.assist_canonicalizer with a text it cannot match ("ping"): the same prompt shape.
  (b) OLLAMA_NUM_PARALLEL=4 made Ollama's memory ESTIMATE (slots x num_ctx) exceed the 20 GB cap: it evicted and
      reloaded models on every request. Back to 3 slots; the small granite lanes share a common first line so they
      occupy ONE cache slot: slots = house prompt / brain / small lanes. Verified: mixed sequence, 0 evictions.
  Rule: watch `journalctl -u ollama | grep -E "evicting|task 0"` after any change; "predicted_num_ctx" = slots x ctx.
- Where a fact question's time goes in the browser: Open WebUI pre-processing ~0.05 s, search 0.6 s, model 1.0-1.6 s
  (reading ~250 new snippet tokens at ~225 tok/s + a 3-token answer), UI socket/render ~0.7 s, so ~2.5-3 s visible.

casa-stt (2026-09-21): own Wyoming STT on the voice host :10310 = Kroko streaming (beam 4 + hotwords + number/name
normalisation) → HA matcher check (match:true) → else the accurate engine. Real-time bench: 0.27/0.33 s avg latency,

First real Echo tests of casa-stt, and what they taught:
  * The FIRST WORD ("turn") was missing from the audio itself: VACA mutes the mic while its wake sound plays, so the
    ~1 s "Ding" swallowed anything said during it. A custom 210 ms "blip" first, then VACA patch v2 (no mic mute at
    all during the blip; vaca-patch/).
  * "Responses after a minute": the Casa conversation context grew 5.5k → 13k tokens across an evening (max_history
    20 kept every tool round of every fuzzy command; each LLM turn then cost 50–80 s and new wake-ups queued behind
    it). max_history 4, later 2.
  * Far-field audio degrades consonants: "monitor light" → "moment"/"monitor lie/like/line", "turn" → "tone/tune",
    people's names → look-alike words. casa-stt repairs transcripts (confusion table + unmatched-slot → closest house
    phrase + vocabulary), validated by the HA matcher; Parakeet fragments ("20%.") no longer win over a better
    streaming text.
  * The LLM acting on fragments is dangerous ("20%." set a light to 20 %): repair + matcher gate avoids most of it.
  * Speakers clip the first ~0.5 s of an HTTP stream: self-test clips need ≥1.5 s lead-in silence.
  * Self-test runs (ai-eval/voice_selftest.py): 7/20 before the fixes, 14/30 after; misses were misheard names and
    wake-word misses (~20 % of speaker plays), never the fast path itself.
  * A runaway 3,300-token generation froze the Echo for 12 min → ollama-guard caps num_predict at 400 for every HA
    request (stt/ollama_guard.py). Deriving a model with `ollama create … FROM granite4.2:3b` + PARAMETERs lost
    granite's chat template (TEMPLATE {{ .Prompt }}) and the copy emitted garbage: never feed
    `ollama show --modelfile` output back into `ollama create` for renderer-based models.
  * Garbled house commands now get "Sorry, I didn't catch that" in <1 s instead of a 30–60 s LLM turn that blocks the
    Echo; questions and general requests still reach the LLM.
  * DEEP DIVE "recordings sound fine, transcripts are bad": 13 real utterances through every engine. Kroko streaming
    8/13 wrong; Parakeet TDT '' or nonsense on 6/13; Whisper small wrong on the hard ones; Whisper medium correct on
    all. Root cause = accent: the small/streaming models were trained on far less accented English than Whisper
    medium. whisper.cpp medium q5_0 on the Arc iGPU (Vulkan) = 1.8 s encode at full 30 s context, 0.3 s with -ac 512
    → ~1.0–1.3 s total per phrase; -nf avoids 10–30 s decoder loops; names-only prompts bias "height" → "light", a
    natural sentence prompt works. casa-stt stage 2 = whisper-server (:10320), Parakeet optional.
